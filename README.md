# YatraCanvas CityPack Lab

YatraCanvas CityPack Lab is the desktop-first human QA, curation, and certification workstation for City Packs generated by [YatraCanvas DataFactory](https://github.com/rohanxgiri/YatraCanvas-DataFactory). It is **not** the YatraCanvas traveller app.

A **City Pack** is the offline package of places, images, and metadata for one city. **Curation** means human corrections stored separately from the generated baseline so they can be reviewed, merged, and reapplied later.

```text
YatraCanvas-DataFactory
        ↓ generates baseline City Packs
YatraCanvas-CityPack_lab
        ↓ human review, corrections, QA, certification
Certified City Pack
        ↓
YatraCanvas traveller app
```

## Who is this for?

### Contributor / curator

Contributors inspect city data, correct names, categories, coordinates and opening hours, replace images, add missing places, exclude bad or duplicate places, complete Manual QA, and submit the resulting files through a Pull Request.

A normal contributor usually needs only this repository:

```text
YatraCanvas-CityPack_lab
```

### Reviewer

Reviewers check focused contributor changes, evidence, image attribution, Manual QA results, and test output before merge.

### Release manager

Release managers create Release Gate evidence, build a certified artifact, and explicitly publish it. Production publication requires all three repositories; see the [Release Manager Guide](docs/RELEASE_MANAGER_GUIDE.md).

## Important: do I need DataFactory?

**For normal CityPack Lab curation: no.**

You do not need `YatraCanvas-DataFactory` or the main `YatraCanvas` repository merely to review and correct the City Packs already committed here. This repository currently includes pack assets for Gulmarg, Jaipur, Manali, Panaji, Rishikesh, Udaipur, and Varanasi.

DataFactory is needed when a release manager imports a newly generated baseline, regenerates source data, or publishes durable curation back into the production data workflow. The main YatraCanvas repository is needed only when publishing or testing a certified pack in the traveller application.

## Prerequisites

- [Git](https://git-scm.com/)
- [Flutter](https://docs.flutter.dev/get-started/install/windows/desktop) stable with Dart `3.13` or newer (the project SDK constraint is `^3.13.0`)
- Windows desktop development requirements reported by `flutter doctor`
- Python 3.12 or newer for curation summaries, certification tests, and release tooling
- Google Chrome only if you want the browser review/development mode

Windows desktop is recommended for real curation. The Chrome build can review the pack, but curation is held in browser memory and local image import cannot write Git-tracked files. Use the Windows app for changes you intend to commit.

## Quick start on Windows

```powershell
git clone https://github.com/rohanxgiri/YatraCanvas-CityPack_lab.git
cd YatraCanvas-CityPack_lab

flutter doctor
flutter pub get

.\citylab.ps1 setup
.\citylab.ps1 start -Target windows
```

The setup command checks Git, Flutter, available devices, dependencies, and the City Packs already present in `assets/city_packs/`. It does not require DataFactory when those committed packs are available.

For browser-only review:

```powershell
.\citylab.ps1 start -Target chrome
```

## Safe Git workflow

Start each city or logical work item from an up-to-date `main` branch:

```powershell
git checkout main
git pull origin main
git checkout -b curate/jaipur-yourname
```

Make corrections through the Windows City Lab app. Before committing:

```powershell
git status
git diff

.\citylab.ps1 summary -City jaipur
.\citylab.ps1 test
flutter analyze
```

`summary` writes `curation_summary.md` as well as printing a short console result. Inspect it and only commit it if the Pull Request intentionally needs that generated report.

Stage only files related to your work, then commit and push your branch:

```powershell
git add assets/city_packs/jaipur/curation/
# If you imported images, also inspect and stage the relevant image folders
# and the corresponding pubspec.yaml change.
git status
git diff --staged

git commit -m "Curate Jaipur opening hours"
git push -u origin curate/jaipur-yourname
```

Open a Pull Request into `main`. Contributors should normally **not** push directly to `main` and should not run production publication.

See [CONTRIBUTING.md](CONTRIBUTING.md) for the complete collaboration workflow and the [Contributor Guide](docs/CITY_LAB_CONTRIBUTOR_GUIDE.md) for the hands-on app walkthrough.

## Safety rules

- **Do not manually edit `yatracanvas.db`.** It is the generated baseline; direct changes are hard to review, cannot be reapplied reliably, and can be overwritten by a later baseline sync.
- Do not fabricate opening hours, coordinates, photos, categories, or source information. Leave uncertain data blank or flag an issue.
- Preserve verifiable image source and licence metadata. Do not use an image if its rights or source cannot be confirmed.
- Do not push directly to `main`; use a focused branch and Pull Request.
- Use **Sync Latest City Packs** to refresh selected baselines. It preserves curation sidecars and imported media, reports changed evidence and safely removes unavailable optional gallery entries.
- Use **Release → View Blockers** before **Build Certified Pack**. Local certified builds require passing gates. Publication is a separate release manager action.
- Inspect `git status`, `git diff`, and `git diff --staged` before committing.
- Do not commit unrelated build output or another contributor's unfinished work.

## Data ownership at a glance

| Layer | Owner | Examples |
|---|---|---|
| Generated baseline | DataFactory | `yatracanvas.db`, `manifest.json`, `city.json`, provider-derived images |
| Human curation | CityPack Lab | overrides, additions, exclusions, reviews, issues, curated media and attribution |
| Production publication | Release manager | certified database, release descriptor, manifests and checksums |

Human curation normally appears under `assets/city_packs/<city>/curation/`; new imported image bytes use `assets/city_packs/<city>/images/curated_<place_id>_<content_hash>/` so baseline sync cannot overwrite them. The baseline SQLite file remains unchanged.

## Daily contributor checklist

```text
Before work
[ ] Update main and create/update a focused feature branch

During work
[ ] Make corrections through the Windows City Lab app
[ ] Cite reliable evidence; never guess
[ ] Coordinate before touching the same place or image as someone else

Before the PR
[ ] Generate the curation summary
[ ] Run tests and analysis
[ ] Inspect status, the working diff, and the staged diff
[ ] Commit only relevant files
[ ] Push the branch and open a Pull Request
```
